RASPBERRY PI ZERO 2 W PERSON DETECTION + GPIO OCCUPANCY CONTROL Complete
Start-from-Scratch Guide
================================================================

PURPOSE

This guide documents the person-detection project built with: -
Raspberry Pi Zero 2 W - IMX219 camera - Quantized MobileNet SSD v1 COCO
model in TensorFlow Lite format - Python, Picamera2, OpenCV, NumPy,
Flask, gpiozero - Live web dashboard - GPIO17 output: HIGH when a person
is detected; LOW after an absence delay

This guide is based on the project setup and troubleshooting discussed.
IP addresses can change, so always check the current address on your Pi.

2. HOW THE PROJECT WORKS

1.  Picamera2 captures frames from the IMX219 camera.
2.  Frames are resized to 300 x 300 pixels for model inference.
3.  TensorFlow Lite runs a quantized MobileNet SSD model.
4.  The model returns detection boxes, class IDs, and confidence scores.
5.  The code considers class ID 0 to be a person for this model.
6.  If person confidence is at least 0.50, GPIO17 becomes HIGH.
7.  If no person is detected for 3 seconds, GPIO17 becomes LOW.
8.  Flask streams annotated video and provides a JSON status endpoint.
9.  A browser dashboard displays video, detection status, GPIO state,
    confidence, inference time, FPS, and errors.

This is visual detection, not guaranteed occupancy sensing. A person
outside the camera’s field of view, hidden behind an object, or missed
in poor lighting may be treated as absent.

3. HARDWARE AND SAFETY

Required: - Raspberry Pi Zero 2 W - IMX219 camera module and compatible
ribbon cable - microSD card with Raspberry Pi OS - Stable power supply
and cable - Network access

Optional: - Suitable relay module or transistor driver - External load
such as a light or indicator

GPIO17 is BCM GPIO17 and physical header pin 11. Physical pin 6 is a GND
pin. GPIO HIGH is approximately 3.3 V and LOW is approximately 0 V.

SAFETY: - Never apply 5 V to a GPIO pin. - Never connect a relay coil or
high-current load directly to GPIO17. - Use a compatible relay module or
transistor driver and suitable supply. - Choose external hardware with a
safe default state. - If the Pi loses power, software cannot guarantee
the external load state.

9. TEST THE MODEL

Create test_model.py: cd ~/person_detector nano test_model.py

Paste this code:

    from pathlib import Path
    from tflite_runtime.interpreter import Interpreter

    model_path = Path("models/detect.tflite")
    if not model_path.exists():
        raise FileNotFoundError(f"Model not found: {model_path}")

    interpreter = Interpreter(
        model_path=str(model_path),
        num_threads=2
    )
    interpreter.allocate_tensors()

    print("Model loaded successfully")
    print("Input details:", interpreter.get_input_details())
    print("Output details:", interpreter.get_output_details())

Save in nano using Ctrl+O, Enter, Ctrl+X.

Run: source .venv/bin/activate python test_model.py

Confirm that the model loads and input shape is [1, 300, 300, 3]. This
test verifies model loading, not detection accuracy.

13. TEST GPIO17 SAFELY

Stop app.py before running a standalone GPIO test, so only one process
controls GPIO17.

Run: python -c “from gpiozero import DigitalOutputDevice; import time;
p=DigitalOutputDevice(17); p.on(); print(‘GPIO17 HIGH’); time.sleep(3);
p.off(); print(‘GPIO17 LOW’); p.close()”

The output should be HIGH for about three seconds and then LOW. Verify
with a multimeter or suitable logic indicator. Do not attach an
unprotected relay coil or high-current load directly.

14. TROUBLESHOOTING: PROBLEMS AND SOLUTIONS

A. TensorFlow Lite Runtime import failure Symptoms: ImportError
importing tflite_runtime.interpreter. Checks: python3 –version python3
-c “import platform; print(platform.machine())” source
~/person_detector/.venv/bin/activate python -m pip show tflite-runtime
Solution: - Confirm the virtual environment is active. - Confirm Python
and CPU architecture compatibility. - Install a compatible
tflite-runtime package. - Do not install a wheel for another
architecture. - The full TensorFlow package is not needed.

B. Model file not found Check: ls -lh
~/person_detector/models/detect.tflite Solution: download/extract the
model again and put it at that exact path.

C. Camera busy Example: RuntimeError: Failed to acquire camera: Device
or resource busy Solution: - Stop rpicam-hello, rpicam-vid, and other
camera scripts. - Run only one camera application at a time. - Stop old
detector processes before restarting app.py.

D. GPIO busy Solution: - Stop the old GPIO test or app that controls
GPIO17. - Do not run a standalone GPIO test while app.py is running. -
Identify a process before stopping it; do not kill unrelated Python
jobs.

E. Browser reports connection refused Possible causes: app.py is not
running, IP address changed, server crashed, or network communication is
blocked. On Pi: hostname -I cd ~/person_detector source
.venv/bin/activate python -u app.py From Windows CMD: ping Then open:
http://:5000 The server must be running while the browser connects.

F. Unexpected restarts or instability During this project, interruptions
occurred while the hardware was moved. The setup became stable after
securing the power connection, suggesting a physical power/cable issue,
although this does not prove every crash has the same cause.
Recommendations: - Use a stable, correctly rated power supply and
cable. - Secure the USB power connector. - Secure the camera ribbon. -
Check logs if the problem returns. A check used during troubleshooting:
vcgencmd get_throttled A result observed at one point was: throttled=0x0
That result only reflects the reported state at that time; it does not
rule out every intermittent power issue.

G. GPIO stays LOW while a person is visible Possible causes: confidence
below threshold, poor lighting, occlusion, incorrect framing, or a model
output/class mismatch. Actions: - Check the live dashboard and
confidence. - Run test_model.py. - Improve camera framing and
lighting. - If needed, cautiously test a lower THRESHOLD, such as 0.40.

H. GPIO goes LOW while someone is still in the room The model can miss a
person due to lighting or occlusion. Increase: NO_PERSON_DELAY = 3.0 For
example, use 5.0 or 10.0 seconds. This reduces switching during short
detection gaps but does not guarantee room occupancy detection.

I. Video/inference is slow Settings used to reduce load: CAMERA_WIDTH =
320 CAMERA_HEIGHT = 240 NUM_THREADS = 2 TARGET_INFERENCE_FPS = 4.0
JPEG_QUALITY = 55 Change one setting at a time and measure results.
Higher resolution and higher inference rates increase processing load.

J. Windows SCP says “No such file or directory” Windows CMD initially
parsed a quoted destination containing backslashes incorrectly. The
destination folder already existed. Use forward slashes in the quoted
SCP destination path as shown in the next section. Also check that the
remote files really exist.

17. SECURITY AND REMOTE ACCESS

The Flask development server is intended for local testing. Do not
expose port 5000 directly to the public internet. For remote access, use
a secure deployment approach with HTTPS and access controls, such as a
properly configured reverse proxy or secure tunnel. Protect the camera
feed and never publish credentials or private camera URLs in GitHub.

18. PERFORMANCE NOTES

An earlier status reading during testing was approximately: -
Confidence: 0.63 - Inference time: 182 ms - FPS: 5.3

These are historical readings, not guaranteed results.

The optimized configuration used: - 320 x 240 camera frames - Two
inference threads - Target inference rate of 4 FPS - JPEG quality 55 -

These settings aim to reduce CPU and network load on the Pi Zero 2 W.

19. LIMITATIONS AND FUTURE IMPROVEMENTS

Limitations: - Detection is limited to the camera field of view. - Poor
lighting and occlusion can cause missed detections. - GPIO behavior
depends on confidence and absence delay. - This is not a certified
security or safety system. - Software cannot control GPIO state during a
full power loss. - Flask development server is not for public production
deployment.

Future improvements: - Dashboard controls for confidence threshold and
absence delay. - Manual GPIO override. - Occupancy event logging. -
Person tracking or temporal filtering. - Evaluation of more efficient
detection models. - Authenticated HTTPS remote viewing. - Proper relay
driver and hardware-level fail-safe design.
